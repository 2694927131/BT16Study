# T03_设备扫描流程详解

> 学习日期：2026-05-16
> 使用工具：Trae + Deepseek-v4-pro
> 状态：已完成

## 关键收获
1. BR/EDR扫描：App→Service→JNI→bluetooth.cc→btif_dm_start_discovery→BTA_DmSearch→BTM_StartInquiry→HCI_Inquiry
2. BLE扫描：走GD层LeScanningManager，不经过btif_dm的传统扫描路径
3. 双模扫描通过同一BTA_DM_SEARCH_CB管理，BR/EDR用HCI_Inquiry，BLE用LE_Scan_Enable
4. 扫描结果逐条上报：EIR解析设备名/CoD/UUIDs/RSSI→invoke_device_found_cb→HAL_CBACK→JNI→Java
5. inquiry进度分4阶段：IDLE→INQUIRY→NAME_DISCOVER(逐个)→COMPLETE，每阶段有明确事件

## 详细笔记

### 一、BR/EDR 扫描流程 (startDiscovery)

**完整调用链**:
```
App: BluetoothAdapter.startDiscovery()
→ Framework → Service → JNI
→ bluetooth.cc L596: do_in_main_thread(btif_dm_start_discovery)
→ btif_dm.cc L2726: btif_dm_start_discovery()
  → L2734: 检查 request_queued (防重复)
  → L2740: btif_dm_inquiry_in_progress = false
  → L2742: BTA_DmSearch(btif_dm_search_devices_evt)
→ bta_dm_api.cc L81: BTA_DmSearch() → bta_dm_disc_start_device_discovery()
→ bta_dm_device_search.cc L799: 投递 BTA_DM_API_SEARCH_EVT
→ bta_dm_device_search.cc L99: bta_dm_search_start()
  → L100: BTM_ClearInqDb() 清空查询数据库
  → L104: 保存回调 p_device_search_cback = btif_dm_search_devices_evt
  → L106: BTM_StartInquiry(bta_dm_inq_results_cb, bta_dm_inq_cmpl_cb)
→ BTM → HCI: HCI_Inquiry (LAP=0x9E8B33, Inquiry_Length=10s, Num_Responses=0)
```

**扫描参数**:
- LAP (Lower Address Part): 0x9E8B33 (General Inquiry Access Code)
- Inquiry_Length: 可配置，默认 10.24 秒
- Num_Responses: 0 = 不限制
- Inquiry_Mode: Standard / With RSSI / With RSSI and EIR

**扫描结果上报流程**:
```
BTM收到Inquiry Response → 回调 bta_dm_inq_results_cb [bta_dm_device_search.cc L174]
→ 构造 tBTA_DM_SEARCH.inq_res:
  - bd_addr: 远端蓝牙地址
  - original_bda: 原始地址(RPA解析后的真实地址)
  - dev_class: 设备类 (Audio/Phone/Computer等)
  - rssi: 信号强度
  - p_eir/eir_len: Extended Inquiry Response (含设备名/UUIDs)
  - ble_addr_type: BLE地址类型
  - inq_result_type: BR/EDR还是BLE
→ p_device_search_cback(BTA_DM_INQ_RES_EVT, &result)  [btif_dm_search_devices_evt]
→ btif_dm_search_devices_evt L1346:
  → BTA_DM_INQ_RES_EVT分支 [L1355]:
    → 已配对设备: 仅上报RSSI/Service UUIDs (保留已有属性)
    → 新设备: 解析EIR获取设备名/UUIDs/CoD/RSSI/Clock Offset
    → invoke_device_found_cb(n, bt_properties) [L1564]
    → HAL_CBACK → JNI → Java: BluetoothDevice.ACTION_FOUND
```

**设备名称获取时机**:
1. **EIR 解析**: Inquiry Response 中的 EIR 数据直接可能包含完整设备名
2. **缓存读取**: btif_storage_get_remote_device_property 读取本地缓存的设备名
3. **Remote Name Request**: inquiry完成后逐个查询未获取到名称的设备
   - L285: btm_status = BTM_ReadRemoteDeviceName(peer_bdaddr, ...)
   - 成功后回调 BTA_DM_NAME_READ_EVT → btif_dm_search_devices_evt→btif_on_name_read

**Inquiry进度分4阶段**:
```
BTA_DM_SEARCH_IDLE         → 初始空闲
BTA_DM_SEARCH_ACTIVE        → Inquiry进行中 (持续收结果)
BTA_DM_SEARCH_CANCELLING    → 用户取消中
BTA_DM_SEARCH_INQUIRY_CANCELLED → Inquiry已取消但要等待NAME_DISCOVER完成
```

**扫描完成后**:
```
Inquiry结束 → BTM: bta_dm_inq_cmpl_cb [L159]
→ bta_dm_inq_cmpl() [L328]
  → BTM_InqDbFirst() 获取第一个设备
  → 逐个查询未获取名称的设备: bta_dm_discover_name()
  → 全部查询完成 → bta_dm_search_cmpl() [L381]
    → p_device_search_cback(BTA_DM_DISC_CMPL_EVT, nullptr)
    → btif_dm_search_devices_evt → 发送 ACTION_DISCOVERY_FINISHED 广播
```

### 二、BLE 扫描流程 (startScan)

BLE 扫描不走 btif_dm_start_discovery 传统路径，而是走 GD 新架构：

```
App: BluetoothLeScanner.startScan()
→ Framework: BluetoothLeScanner → GattService
→ GD: LeScanningManager (gd/hci/le_scanning_manager/)
  → HCI: LE_Set_Scan_Parameters
    - LE_Scan_Type: Passive(0x00)/Active(0x01)
    - LE_Scan_Interval: 扫描间隔 (N x 0.625ms)
    - LE_Scan_Window: 扫描窗口 (N x 0.625ms)
    - Own_Address_Type: Public/Random
    - Scanning_Filter_Policy: Accept All/Whitelist Only
  → HCI: LE_Set_Scan_Enable (Scan_Enable=1, Filter_Duplicates=1)

扫描结果上报:
HCI: LE_Advertising_Report Event
→ GD: LeScanningManager 解析
→ GattService → Java: ScanCallback.onScanResult()
```

**三种扫描模式**:
| 模式 | 间隔 | 窗口 | 功耗 |
|------|------|------|------|
| SCAN_MODE_LOW_LATENCY | 小间隔(~10ms) | 大窗口 | 高 |
| SCAN_MODE_BALANCED | 中等(~100ms) | 中等 | 中 |
| SCAN_MODE_LOW_POWER | 大间隔(~1s) | 小窗口 | 低 |

**扫描过滤机制**:
1. **ScannerSettings.setScanMode()**: 配置扫描模式
2. **ScanFilter**: 按 Service UUID / Device Address / Service Data 过滤
3. **Filter_Duplicates**: HCI层过滤重复广播包过滤
4. **ScanSettings.setMatchMode()**: STICKY(同一个设备存一份)/AGGRESSIVE(每次更新都上报)

### 三、双模扫描

**两个扫描能否同时进行？**
- 技术上可以：BR/EDR Inquiry 和 BLE Scan 使用不同 HCI 命令，互不阻塞
- 代码上共用同一个 SearchCB(bta_dm_search_cb)，但 bta_dm_inq_results_cb 能同时处理两种结果
- 传统 startDiscovery 也会触发 BLE 扫描（`BLE_ADV_SCAN`），来自 inquiry 结果中的 LE 设备信息

**Android 处理双模扫描的方式**:
- bta_dm_device_search.cc 中 bta_dm_inq_results_cb 区分设备类型:
  - `inq_result_type == BT_DEVICE_TYPE_BLE` → 来自 BLE 扫描
  - 否则 → 来自 BR/EDR Inquiry
- 两种结果都通过同样的回调链上报

### 四、关键数据结构

**扫描结果在每一层的表示**:
```
C++ (BTIF): bt_property_t[] = {BDADDR, RSSI, BDNAME, COD, UUIDS, ...}
C++ (BTA): tBTA_DM_SEARCH = {inq_res: {bd_addr, dev_class, rssi, p_eir, ...}}
HCI: Inquiry Result Event / Extended Inquiry Result Event

Java (Framework): BluetoothDevice + 广播 Intent
- ACTION_FOUND: Intent 中 putExtra(DEVICE, device) + putExtra(RSSI, rssi)
- EXTRA_CLASS: 设备类
- EXTRA_NAME: 设备名称
```

**BluetoothDevice 对象创建时机**:
- 首次收到扫描结果时创建
- 不重复创建：通过 `BTM_InqDbRead(bdaddr)` 检查是否已在查询数据库
- 设备名从缓存读取或后续 Remote Name Request 获取

### 五、常见问题

**扫描不到设备的可能原因**:
1. 蓝牙芯片未就绪 → 检查蓝牙是否 ON
2. Inquiry 已在进行中 → bta_dm_is_search_request_queued() 返回 true (有pending)
3. inquiry busy → btif_dm_inquiry_in_progress = true
4. Interop 限制: DISABLE_NAME_REQUEST 的设备被跳过名称查询
5. BLE 设备不在可连接广播中: `is_connectable` 检查过滤
6. 扫描窗口/间隔设置太短

**扫描结果丢失/重复的处理**:
- 丢失: EIR 长度超限时数据被截断
- 重复: HCI 层 Filter_Duplicates=0 会收到重复包
- 解决: HCI Filter_Duplicates=1 + 已配对设备特殊处理(L1363检查)
- 缓存: 对已配对设备使用 get_cached_remote_name 避免重复 RNR

**扫描对已连接设备的影响**:
- Inquiry 会占用蓝牙芯片时间槽，可能影响现有 ACL 连接质量
- 音频播放中不推荐长时间扫描
- Android 会在扫描时调整连接参数以保证数据传输
