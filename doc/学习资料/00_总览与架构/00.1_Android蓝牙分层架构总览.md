# 00.1 Android 蓝牙分层架构总览

> 速通摘要（一段话版）：Android 蓝牙是一栋**七层楼**——最上面是 App（你写的或 Settings），下面是 Framework Java API（`BluetoothAdapter` 等），再下面是 system_server 里的 `BluetoothManagerService`（Kotlin），它通过 Binder 把请求转发到独立进程的"蓝牙 App"（`com.android.bluetooth`），蓝牙 App 里的 `AdapterService` 通过 JNI 走到 C++ 世界，C++ 世界再分成 BTIF（适配层）→ BTA（业务状态机）→ Stack（协议）→ GD（新模块化栈）→ HAL（厂商芯片驱动）。**记住"上 Java 下 C++、中间靠 JNI"，其余都是细节。**

## 3. 场景故事：你在车机上点了"打开蓝牙"

把车上发生的事拍成慢动作：

1. **HMI**：你点了开关按钮。Car Settings App 调了 `BluetoothAdapter.enable()`。
2. **Framework API（Java，进程：当前 App）**：`BluetoothAdapter` 把请求打包成 Binder 调用，目标是 `system_server` 中的 `IBluetoothManager`。
3. **BluetoothManagerService（Kotlin，进程：`system_server`）**：作为"系统级守门员"，它检查权限、飞行模式、用户开关、上次崩溃次数，然后**启动**蓝牙 App 进程（`com.android.bluetooth`），并告诉它："开机"。
4. **AdapterService（Java，进程：`com.android.bluetooth`）**：蓝牙 App 的中枢。它初始化各 Profile Service，然后调 `AdapterNativeInterface.enable()`。
5. **JNI（C++，同进程）**：`AdapterNativeInterface_enableNative` 把 Java 调用翻译成 C 调用，跳进 BTIF 层的 `bluetooth.cc`。
6. **BTIF（C++，同进程）**：BTIF 是"适配 + 编排"层。它告诉 stack_manager："初始化栈，并把 profile 起来"。
7. **BTA + Stack（C++，同进程）**：BTA（业务状态机）和 Stack（协议）开始按部就班——加载配置、初始化 HCI、向控制器发 HCI Reset、等待 HCI Command Complete。
8. **GD + HAL（C++，同进程）**：GD 层（`system/gd/hal/`）和 HAL 之间用 AIDL 通信（HAL 在独立进程 `android.hardware.bluetooth-service.*`）。HAL 进程把 HCI 命令通过物理通道（UART/USB/SDIO）下发给蓝牙芯片。
9. **芯片**：芯片复位，回 HCI Event。
10. **回程**：HAL → GD → Stack → BTA → BTIF → JNI 回调 → Java `JniCallbacks` → 派发到 `AdapterProperties` 与 `AdapterState`（这是一个 Android 风格的 `StateMachine`）→ 进入 `STATE_ON`。
11. **广播**：`AdapterService` 发出 `BluetoothAdapter.ACTION_STATE_CHANGED`，HMI 收到后把开关 UI 翻成蓝。

**车载现实**：这一整套要在几百毫秒内完成。出问题的位置可能在任意一层。学完这套架构，遇到 bug 你就有 7 个调查切入点。

**记忆口诀**：
- Java 三段：App → `BluetoothAdapter` → `BluetoothManagerService` → `AdapterService`。

- 跨进程到芯片：GD → HAL → 芯片。

## 5. 七层楼详解

### 5.1 第 7 层：App（Settings / Car HMI / 第三方）
- 写的是 Java/Kotlin，进程随 App。
- 入口是 `BluetoothAdapter.getDefaultAdapter()`（已 deprecated）或 `context.getSystemService(BluetoothManager.class).getAdapter()`。
- 受 `BLUETOOTH_CONNECT` / `BLUETOOTH_SCAN` / `BLUETOOTH_ADVERTISE` 等运行时权限约束。
- **车机定制热点**：Car Settings 通常是车厂自研，**不在本仓库内**——你看到的 Settings 行为问题往往得去车厂自己的 git 仓找。

### 5.2 第 6 层：Framework Java API
- 文件：`framework/java/android/bluetooth/`。
- 角色：把 App 的 Java 调用打包成 Binder，目标是 `system_server` 或蓝牙 App 进程。
- 关键类（节选）：
  - `BluetoothAdapter` — `framework/java/android/bluetooth/BluetoothAdapter.java:143`
  - `BluetoothDevice` — `framework/java/android/bluetooth/BluetoothDevice.java`
  - `BluetoothManager` — 通过 `Context.getSystemService(BLUETOOTH_SERVICE)` 返回
  - `BluetoothProfile` — Profile 抽象基类
- **本质**：这一层几乎没有业务逻辑，主要是参数校验、权限检查、Binder 转发。

### 5.3 第 5 层：BluetoothManagerService（Kotlin / system_server）
- 文件：`service/src/`（本仓库，Kotlin 实现）。
- 进程：`system_server`（不是蓝牙 App 进程！）。
- 关键文件：
  - `service/src/BluetoothService.kt` — Service 主体
  - `service/src/AdapterBinder.kt` — 与 `AdapterService` Binder 对接
  - `service/src/AdapterState.kt` — 顶层蓝牙开关状态机
  - `service/src/BluetoothSupervisor.kt` — 监管蓝牙 App 进程生命周期
- 职责：
  1. 接收 App 的开关请求，做策略层判断（飞行模式、用户、政策）。
  2. **启动 / 杀掉蓝牙 App 进程**——蓝牙 App 跟 system_server 是两个进程。
  3. 给上层暴露 `BluetoothAdapter` 真正背后的 Binder。
- **历史注**：Android 早期 `BluetoothManagerService` 是 Java 写的、放在 `frameworks/base/services/`；Android 13 起逐步迁到这个 Kotlin Mainline 模块。

### 5.4 第 4 层：AdapterService（蓝牙 App 主进程）
- 文件：`android/app/src/com/android/bluetooth/btservice/AdapterService.java`（5030 行）。
- 进程：`com.android.bluetooth`（独立 App，AOSP 的 Mainline 模块）。
- 职责：
  1. 蓝牙 App 的"总管"——所有 Profile Service（A2DP、HFP、GATT…）由它启动/停止。
  2. 实现 `IBluetooth` AIDL（见 `AdapterServiceBinder.java`）。
  3. 管理 `AdapterProperties`（地址、名称、scan_mode 等）、`AdapterState`（开关状态机）、`RemoteDevices`（已知设备表）、`BondStateMachine`（配对状态机）。
  4. 通过 `AdapterNativeInterface` 调 JNI，通过 `JniCallbacks` 接 JNI 回调。
- 关键邻居：
  - `AdapterServiceBinder.java` — Binder 接口
  - `AdapterNativeInterface.java` — Java→Native 出口
  - `JniCallbacks.java` — Native→Java 入口
  - `BondStateMachine.java`、`RemoteDevices.java`、`PhonePolicy.java`、`ActiveDeviceManager.java`

### 5.5 第 3 层：JNI（C++）
- 文件：`android/app/jni/`。
- 同进程（仍在 `com.android.bluetooth`）。
- 关键：`com_android_bluetooth_btservice_AdapterService.cpp` — `AdapterService` 的 Native 对端。
- 职责：
  1. `JNI_OnLoad` 注册 Java 方法 ↔ C 函数映射。
  2. 把 Java 类型翻译成 C++ 类型（`jstring` → `std::string` 等）。
  3. 调用 BTIF 提供的 C 接口（如 `bt_interface_t->enable()`）。
  4. 注册 Native 回调，等异步事件回来后通过 `JNIEnv->CallVoidMethod` 调回 Java。

### 5.6 第 2 层：BTIF / BTA / Stack（C++ 协议栈三人组）
- 三者通常被合称为"native bluetooth stack"，全部在 `com.android.bluetooth` 进程里、同地址空间。

**BTIF（适配层）** — `system/btif/`
- 是 JNI 与下层栈之间的"接线员"。
- 对上暴露 `bt_interface_t`（C 函数表）；对下调 BTA 接口。
- 入口：`system/btif/src/bluetooth.cc`（提供 `bt_interface_t` 实现）、`system/btif/src/stack_manager.cc`（栈初始化）。
- 各 Profile 各有一个 btif 文件：`btif_av.cc`、`btif_hf.cc`、`btif_gatt.cc`、`btif_dm.cc`（设备管理）。

**BTA（业务状态机层）** — `system/bta/`
- 把 Profile 业务抽象成状态机。
- 每个子目录就是一个业务：`av/` 是 A2DP/AVRCP，`ag/` 是 HFP AG，`hf_client/` 是 HFP HF，`dm/` 是设备管理，`gatt/` 是 GATT，等等。
- 上面被 BTIF 调用，下面调 Stack 的 API。

**Stack（协议层）** — `system/stack/`
- 真正的"蓝牙协议栈"。
- 关键子目录：
  - `btm/` — Base Manager（Inquiry / Bond / SCO 上层）
  - `acl/` — ACL 链路管理
  - `l2cap/` — 逻辑通道与多路复用
  - `sdp/` — SDP 服务发现
  - `rfcomm/` — RFCOMM 串口仿真
  - `smp/` — SMP 安全管理（BLE）
  - `gatt/`、`eatt/` — GATT / Enhanced ATT
  - `avdt/`、`avct/`、`avrc/`、`a2dp/` — 音频协议族
  - `hcic/` — HCI Command 构造
  - `hid/`、`bnep/`、`pan/` 等

### 5.7 第 1 层：GD（Gabeldorsche）模块化栈
- 文件：`system/gd/`。
- 这是 Google 自 Android 11 起重写的"下一代蓝牙栈"，目标是模块化、可测试、跨平台（Linux Floss 也用它）。
- **现状（Android 16）**：HCI 收发、HAL 对接、Storage、Metrics 等"基础设施"模块已经搬到 GD；而 L2CAP / RFCOMM / GATT 等"协议实现"大体还在传统 Stack 中。GD 与传统 Stack 通过 `system/main/shim/` 互通。
- 关键子目录：
  - `gd/hal/` — HAL 接口与实现（与 HAL 进程对接）
  - `gd/hci/` — 新 HCI 层（packet 编解码、command queue）
  - `gd/os/` — OS 抽象
  - `gd/packet/` — Packet 解析框架
  - `gd/storage/` — 配置/绑定信息持久化
  - `gd/metrics/` — 指标上报

### 5.8 第 0 层：HAL 与芯片
- HAL 进程：`android.hardware.bluetooth-service.*`（**外部依赖**，本仓库不含 HAL 厂商实现）。
- HAL 通过 AIDL 把 HCI 命令/事件转发给芯片，物理传输通常是 UART / USB / SDIO。
- HAL 接口定义在 `hardware/interfaces/bluetooth/aidl/`（**AOSP 其他仓**）。

## 7. 简化代码片段（带注释）

下面给两段最具代表性的"层间衔接"代码，先建立直观印象（具体每行都会在后续章节详解）。

### 7.1 Java → JNI 出口（节选）

```java
// android/app/src/com/android/bluetooth/btservice/AdapterNativeInterface.java
public class AdapterNativeInterface {
    // Java 端声明的 native 方法。运行时由 JNI_OnLoad 注册成对应的 C++ 函数。
    private native boolean enableNative();
    private native boolean disableNative();
    // …很多 native 方法…

    boolean enable() {
        return enableNative();   // 一句 Java 调用，跨过语言屏障跳进 C++。
    }
}
```

Java 类比：你写 Android 时调用过 `System.loadLibrary("xxx")` 配合 `native` 方法吗？蓝牙模块就是放大版的这个模式，只是 library 是 `libbluetooth_jni.so`。

### 7.2 JNI → BTIF 出口（节选示意）

```cpp
// android/app/jni/com_android_bluetooth_btservice_AdapterService.cpp（节选示意）
static jboolean enableNative(JNIEnv* env, jobject obj) {
    // sBluetoothInterface 是 BTIF 提供的全局函数表 (bt_interface_t*)
    // 该表来自 system/btif/src/bluetooth.cc 的 bluetoothInterface 全局
    if (!sBluetoothInterface) return JNI_FALSE;
    int ret = sBluetoothInterface->enable();
    return (ret == BT_STATUS_SUCCESS) ? JNI_TRUE : JNI_FALSE;
}
```

> 真实代码里包了 `ScopedJniThreadState`、错误处理、metric 上报等细节；本节只看主干。

## 8. 调试方法

| 想看什么 | 工具 / 命令 |
|----------|-------------|
| Java 侧日志（开关、配对、状态变化） | `adb logcat -s BluetoothAdapter BluetoothManagerService AdapterService` |
| Native 侧日志 | `adb logcat -s bluetooth bt_btif bt_btm bt_l2cap bt_gatt bt_hci` |
| 蓝牙 App 进程是否还活着 | `adb shell pidof com.android.bluetooth` |
| 蓝牙状态全景（最重要的一句命令） | `adb shell dumpsys bluetooth_manager` |
| HCI 抓包（看主控 ↔ 芯片真实通信） | `adb shell setprop persist.bluetooth.btsnooplogmode full && adb shell svc bluetooth disable && adb shell svc bluetooth enable`，然后取 `/data/misc/bluetooth/logs/btsnoop_hci.log` |
| 验证某层是否启动 | 看 logcat 里 `init_stack`、`event_start_up_stack`、`Profile init` 关键字 |

> ⚠️ 在某些车机上，`btsnoop` 路径与 selinux 策略可能不同。如果取不出文件，先 `adb root` 再 `adb shell ls /data/misc/bluetooth/logs/`。

## 9. FAQ

**Q1：`BluetoothManagerService` 不是早就 Java 写在 `frameworks/base` 吗？**
A：从 Android 13 起 Google 把它逐步迁到 Mainline 模块，并改用 Kotlin。本仓的 `service/src/` 就是这一代实现。旧 Java 版你可能在某些厂商定制中还能见到。

**Q2：蓝牙 App（`com.android.bluetooth`）和 `system_server` 是同一个进程吗？**
A：**不是**。蓝牙 App 是独立进程，由 `BluetoothManagerService` 拉起来。这意味着蓝牙崩溃不会拖死 `system_server`；调试时也要分别看两个进程的 logcat。

**Q3：BTIF / BTA / Stack 是三个进程吗？**
A：不是，是三个**代码层**——都跑在蓝牙 App 进程同一个地址空间里。

**Q4：HAL 在哪个进程？**
A：HAL 在**独立进程**（`android.hardware.bluetooth-service.*`），与蓝牙 App 通过 AIDL（Binder）通信。HAL 厂商实现**不在本仓库**。

**Q5：GD 已经取代旧 Stack 了吗？**
A：没有完全取代。Android 16 里 GD 主要承担基础设施（HCI、HAL 对接、Storage、Metrics 等）；L2CAP/RFCOMM/GATT 等高层协议大体仍在传统 `system/stack/`。两者通过 `system/main/shim/` 互通。

 7. App
