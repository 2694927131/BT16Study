# 11.7 通用排查方法论

> 速通摘要：所有车机蓝牙问题用同一套**5 步方法论**搞定：① 复现 ② 取证 ③ 分层定位 ④ 假设验证 ⑤ 修复回归。本节是全书排查章的**总章**——任何问题都套用这套流程。

---

## 1. 学习目标

读完本节，你应该能：

1. 把"模糊的用户投诉"转换成"具体的栈层问题"。
2. 用 5 步方法论解决任意一个新蓝牙 bug。
3. 写出可复用的排查脚本。

---

## 2. 5 步方法论

### Step 1：复现
**找到一组操作让 bug 100% 出现**。
- 写下操作步骤（设备型号、版本、环境）。
- 排除偶发因素（开蓝牙重做一次）。
- 准备测试环境（root、userdebug 镜像）。

如果不能稳定复现 → 让 QA 提供 frequency；本身就是排查信息。

---

### Step 2：取证
**一次复现尽可能多收集**。

```bash
#!/bin/bash
# bt_evidence.sh
TS=$(date +%s)
OUT=/tmp/bt_$TS
mkdir -p $OUT

# 1. 状态快照
adb shell dumpsys bluetooth_manager > $OUT/dumpsys_bm.txt
adb shell dumpsys audio > $OUT/dumpsys_audio.txt
adb shell dumpsys telecom > $OUT/dumpsys_telecom.txt
adb shell dumpsys media.audio_policy > $OUT/audio_policy.txt
adb shell dumpsys media.audio_flinger > $OUT/audio_flinger.txt

# 2. logcat（全量）
adb logcat -d > $OUT/logcat.txt

# 3. BTSnoop
adb pull /data/misc/bluetooth/logs/btsnoop_hci.log $OUT/ 2>/dev/null

# 4. 配置
adb shell cat /data/misc/bluedroid/bt_config.conf > $OUT/bt_config.conf 2>/dev/null

# 5. 系统
adb shell getprop | grep -i blueto > $OUT/sysprops.txt
adb shell ps -A | grep -i blueto > $OUT/processes.txt
adb shell ls -la /apex/com.android.btservices/ > $OUT/apex.txt

# 6. tombstone（如果 native crash）
adb shell ls -la /data/tombstones/ > $OUT/tombstones.txt
adb pull /data/tombstones/ $OUT/tombstones/ 2>/dev/null

echo "Saved to $OUT"
```

---

### Step 3：分层定位
**用 7 层楼模型逐层缩范围**。

```
1. UI 层      → 是否 HMI 端的事？（用基础 App 替代验证）
2. App 层     → 是否 App 实现的问题？
3. Framework → Binder 是否到达？看 logcat BluetoothAdapter
4. BMS        → system_server 端策略？看 BluetoothManagerService
5. AdapterSvc → 蓝牙 App 主进程？看 AdapterService / 状态机
6. JNI        → Java→Native 是否过去？看 native log
7. BTIF/BTA   → 业务编排？看 bt_btif_* / bt_bta_*
8. Stack      → 协议层？看 bt_btm/bt_l2cap/bt_avdt/...
9. GD/HAL     → HCI/HAL？看 btsnoop
10. 控制器    → 芯片本身？看 HCI status code + tombstone
```

每层都有"关键日志 / dumpsys 段 / btsnoop 段"对应。逐层"是否经过"判断。

---

### Step 4：假设验证
**做出最小可证伪的假设**。

例：
- 假设 "Active Device 切错"。
- 验证：dumpsys 看 Active A2DP device 是不是当前手机？不是就证实。

每个假设：
1. 用一句话写下。
2. 列出验证它/否定它的最少操作。
3. 做完后留笔记。

**绝对不要**："感觉是 codec 问题，我改改 codec 试试" —— 没假设、没验证、没回溯。

---

### Step 5：修复回归
**修了一定要回归验证**。

修复后：
1. 跑一次"复现步骤"，确认 bug 消失。
2. 跑一次"邻近场景"，确认没引入新 bug。
3. 跑一次单元测试 / 集成测试。
4. 留下"修复说明 + 验证步骤" 文档。

## 3. 实战 Case：用方法论解决一个真实问题

**投诉**：用户报"开车 30 分钟后蓝牙音乐不响了，重连后又好"。

### Step 1: 复现
- 模拟"30 分钟" → 改成"在测试机上长跑"。
- 半小时后果然出现：A2DP 状态变 DISCONNECTED。

### Step 2: 取证
- 跑 §2 脚本。

### Step 3: 分层定位
- dumpsys A2DP: state=DISCONNECTED；before 30min 是 CONNECTED。
- logcat 搜 "DISCONNECTED"：找到 `aclStateChangeCallback DISCONNECTED reason=0x08`。
- 0x08 = Connection Timeout。
- btsnoop：30 分钟点前 6 秒，HCI ACL 数据流停了，然后 Disconnect。
- 结论：ACL 链路因 supervision timeout 断了。

### Step 4: 假设验证
- 假设："因为 ACL 长时间无心跳，supervision timeout 触发"。
- 验证：把 supervision timeout 调大，再跑 1 小时——果然好了。
- 反过来：把 supervision timeout 设到 10 秒，10 秒后必断——再证实。

### Step 5: 修复回归
- 修复：调整 LE Connection 默认参数或 sysprop。
- 回归：4 种场景 × 2 小时 = 8 小时 long run，无断开。

## 7. 本节小结

```
5 步方法论：
  ① 复现   找到 100% 触发的操作
  ② 取证   dumpsys + logcat + BTSnoop + sysprop + tombstone 一并抓
  ③ 分层   按 7 层楼 + 关键日志/段/帧定位到具体层
  ④ 假设   每个假设最小可证伪 + 验证
  ⑤ 修复   修完回归 + 写下文档

工具沉淀：脚本 + wiki + 自动巡检
反模式：
  - 没假设盲改
  - 一次只看一个工具
  - 修了不回归
  - 不留文档
```
