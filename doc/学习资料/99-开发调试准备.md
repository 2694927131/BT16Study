# 99. 开发调试准备：编译、刷机、日志、snoop 与常用 adb

## 1. 为什么放在最后

本章按要求延后处理。前面章节先把蓝牙源码结构、基础链路、JNI/Native、A2DP、HFP、BLE/GATT、手机互联和故障排查建立起来；现在再补开发调试准备，读命令时就能知道它们对应哪条链路。

当前仓库是 Bluetooth 模块源码，完整 Android 产品编译、刷机脚本、设备分区和厂商配置可能在外部工程。本章只写通用准备和当前仓库可验证的观察点。

## 2. 环境准备清单

| 项目 | 说明 |
| --- | --- |
| Android 源码环境 | 需要能进入完整 AOSP/产品工程后执行 `source build/envsetup.sh`、`lunch` |
| 设备连接 | `adb devices` 能看到目标车机/开发板 |
| 日志权限 | userdebug/eng 更适合抓取完整蓝牙日志和 snoop |
| 源码索引 | 在本仓库使用 `rg` 查 Java/JNI/Native 链路 |
| 复现脚本 | 每类问题固定复现步骤和时间戳 |

## 3. 编译准备

完整构建命令依赖外部产品工程。常见流程如下：

```bash
source build/envsetup.sh
lunch <product>-userdebug
m Bluetooth
```

如果产品工程支持模块化构建，也可能使用：

```bash
m com.android.btservices
m bluetooth
```

当前仓库内建议先做源码级检查：

```bash
rg -n "class AdapterService|class GattService|class A2dpService" android/app/src
rg -n "JNINativeMethod|register_com_android_bluetooth" android/app/jni
rg -n "btif_.*connect|BTA_.*Open|GATT_Connect" system
```

## 4. 刷机与部署边界

刷机方式取决于产品工程和设备：

```bash
adb reboot bootloader
fastboot devices
fastboot flash <partition> <image>
fastboot reboot
```

蓝牙模块可能涉及 system、product、system_ext、apex 或 vendor 组合，具体以项目构建产物为准。不要只替换一个 APK 就假设 Native 栈也更新了；JNI、BTIF、Stack、配置文件可能位于不同镜像或 APEX 中。

## 5. 日志抓取

基础日志：

```bash
adb logcat -b all -v threadtime > bluetooth.log
adb shell dumpsys bluetooth_manager > bluetooth_manager.txt
adb shell dumpsys bluetooth > bluetooth.txt
```

按关键词观察：

```bash
adb logcat -b all | grep -i "AdapterService\|BondStateMachine\|A2dpService\|HeadsetClient\|GattService"
adb logcat -b all | grep -i "bt_stack\|btif\|bta\|gatt\|hfp\|a2dp"
```

问题复现时至少记录：

- 开始复现时间。
- 点击或连接动作。
- 失败出现时间。
- 对端设备地址和名称。
- 当时连接了哪些 Profile。

## 6. HCI snoop

HCI snoop 用于确认 controller 层有没有真实空口事件。不同产品开启方式可能不同，常见检查点：

```bash
adb shell getprop | grep -i snoop
adb shell ls /data/misc/bluetooth/logs
adb pull /data/misc/bluetooth/logs ./bluetooth_logs
```

如果设备支持开发者选项，可打开“启用蓝牙 HCI 信息收集日志”。抓到的 snoop 文件可用 Wireshark 打开。

怎么看 snoop：

| 问题 | snoop 里看什么 |
| --- | --- |
| 搜不到 Classic 设备 | Inquiry / Inquiry Result |
| BLE 扫不到 | LE Advertising Report |
| 配对失败 | SMP Pairing / SSP / Authentication Complete |
| A2DP 失败 | L2CAP、AVDTP signaling/media |
| HFP 失败 | RFCOMM、AT command、SCO/eSCO |
| GATT 失败 | ATT Read/Write/Handle Value Notification |

## 7. dumpsys 观察

常用：

```bash
adb shell dumpsys bluetooth_manager
adb shell dumpsys bluetooth
adb shell dumpsys activity services | grep -i bluetooth
```

重点看：

- Adapter state 是否 ON。
- Bonded devices 是否包含目标设备。
- Profile connection state。
- Active device。
- GATT client/server、scanner 状态。
- 最近的错误日志或 native crash。

## 8. 源码断点与搜索路线

如果能本地调试 Java：

- 开关：`AdapterService`、`AdapterState`
- 配对：`BondStateMachine`
- A2DP：`A2dpService`、`A2dpStateMachine`
- HFP：`HeadsetClientService`、`HeadsetClientStateMachine`
- BLE：`GattService`、`ScanController`、`ScanManager`

Native 搜索路线：

```bash
rg -n "register_com_android_bluetooth" android/app/jni
rg -n "btif_.*connect|btif_.*open" system/btif/src
rg -n "BTA_.*Open|BTA_.*Connect|BTA_.*Search" system/bta
rg -n "GATT_Connect|GATTC_Read|GATTC_Write|L2CA_|RFCOMM" system/stack
```

## 9. 调试纪律

1. 先确认问题属于哪个 Profile 或基础链路。
2. 每次只改一个变量：手机、车机版本、是否清除配对、是否重启蓝牙。
3. Java 日志、Native 日志、dumpsys、snoop 时间戳要对齐。
4. 能用源码证明的写源码路径，不能证明的标注为外部依赖。
5. 复现后立即保存日志，避免 logcat ring buffer 覆盖。

## 10. 最小交付包

给开发同事或供应商定位时，建议提供：

- 问题描述和复现步骤。
- 车机版本、手机型号和系统版本。
- 目标设备地址。
- `bluetooth.log`。
- `bluetooth_manager.txt` 和 `bluetooth.txt`。
- HCI snoop 文件。
- 初步判断：Java/JNI/BTIF/BTA/Stack/Controller/外部互联协议。
