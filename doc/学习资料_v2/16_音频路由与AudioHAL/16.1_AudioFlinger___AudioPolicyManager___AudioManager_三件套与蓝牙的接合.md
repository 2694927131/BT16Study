<!--
已知陷阱（生成时必须注意）：
  - 不要把 AudioFlinger 和 Audio HAL 混为一谈
      AudioFlinger 是 Android 侧的混音引擎（运行在 media.audio_flinger 进程），
Audio HAL 是 AudioFlinger 与硬件之间的 HAL 层（HIDL/AIDL 服务）。
蓝牙的 audio_hal_interface（BluetoothAudioClientInterface）是蓝牙侧实现的 Audio HAL Client，
对端是 BluetoothAudioProvider（HAL Server，由芯片厂商/OEM 实现，不在本仓库）。
调试时不要把 AudioFlinger 日志和 bluetooth audio_hw 日志混用。

  - 不要假设 Audio HAL 一定走 AIDL
      HalVersionManager 在运行时检测，旧设备（Android 12 及以下）走 HIDL 2.0/2.1，
Android 13+ 才普遍迁移到 AIDL。车机 OEM 可能因芯片供应商的 Audio HAL 还是 HIDL
而锁定在 HIDL 路径。遇到 Audio Session 问题先看 `HalVersionManager::GetHalVersion()`
的日志确认当前路径，再找对应的 client_interface_hidl 或 client_interface_aidl。

  - 不要把 setActiveDevice 误解为直接切音频
      setActiveDevice 只是通知 Profile Service 更新"当前活跃设备"记录，
真正的音频切换发生在 AudioPolicyManager 收到 AudioDeviceCallback 回调后重路由时。
这两步之间有异步间隔（通常 50-200ms），在日志中能看到 setActiveDevice 先打印，
AudioPolicyManager onAudioPortChanged 后打印。

  - 车机多手机接入时 ActiveDeviceManager 只有一套 Active Device
      AOSP 的 ActiveDeviceManager 每个 Profile（A2DP/HFP/LE Audio）只维护一个 Active Device。
车机同时连两部手机时，只有一部是 A2DP Active（音乐），另一部会"静默"在连接态。
OEM 如果要实现"双手机都能接电话"，需要扩展 ActiveDeviceManager 的仲裁逻辑（属于 OEM 定制，
不是 AOSP 标准行为）。

  - 不要在没有 Audio HAL Provider 的环境（如模拟器）调试音频路由
      BluetoothAudioClientInterface::StartSession() 依赖 IBluetoothAudioProvider AIDL 服务，
模拟器上通常没有这个 HAL 实现，StartSession 会返回 -EINVAL。
在真机上调试时注意：OEM 的 Audio HAL 可能对某些 AudioConfiguration（如 LC3 offload）
返回 EX_ILLEGAL_ARGUMENT，需要先用 GetAudioCapabilities 确认支持的配置。

-->

### 片段：snippet_active_device_manager_a2dp

**来源**：`android/app/src/com/android/bluetooth/btservice/ActiveDeviceManager.java:1044-1078`

```java
// L1044
private boolean setA2dpActiveDevice(
        @Nullable BluetoothDevice device, boolean hasFallbackDevice) {
    Log.d(TAG, "setA2dpActiveDevice(" + device + ")"
            + (device == null ? " hasFallbackDevice=" + hasFallbackDevice : ""));
    synchronized (mLock) {
        if (mPendingActiveDevice != null) {
            mHandler.removeCallbacksAndMessages(mPendingActiveDevice);
            mPendingActiveDevice = null;
        }
    }
    final var a2dp = mAdapterService.getA2dpService();
    if (a2dp.isEmpty()) {
        return false;
    }
    boolean success = false;
    if (device == null) {
        success = a2dp.get().removeActiveDevice(!hasFallbackDevice);
    } else {
        success = a2dp.get().setActiveDevice(device);
    }
    if (!success) {
        return false;
    }
    synchronized (mLock) {
        mA2dpActiveDevice = device;
    }
    return true;
}
```

ActiveDeviceManager 是 A2DP / HFP / LE Audio 三路音频的"仲裁者"：当设备连接/断开/
优先级变化时，由它决定谁是当前活跃设备，并调用各 Profile Service 的 setActiveDevice()。
device == null 表示"清除活跃设备"（例如耳机拔出），hasFallbackDevice 告诉 A2DP
是否还有备选设备可切换——若无则彻底停止蓝牙音频路由。
mLock 是 synchronized，对应 C++ 的 std::mutex；整个方法是三路互斥中的 A2DP 分支。

### 片段：snippet_bluetooth_audio_start_session

**来源**：`system/audio_hal_interface/aidl/client_interface_aidl.cc:332-360`

```cpp
// L332
int BluetoothAudioClientInterface::StartSession() {
  std::lock_guard<std::mutex> guard(internal_mutex_);
  if (provider_ == nullptr) {
    log::error("BluetoothAudioHal nullptr");
    session_started_ = false;
    return -EINVAL;
  }
  if (session_started_) {
    log::error("session started already");
    return -EBUSY;
  }
  std::shared_ptr<IBluetoothAudioPort> stack_if =
          ndk::SharedRefBase::make<BluetoothAudioPortImpl>(transport_, provider_);
  std::unique_ptr<DataMQ> data_mq;
  DataMQDesc mq_desc;
  auto aidl_retval = provider_->startSession(
          stack_if, transport_->GetAudioConfiguration(),
          latency_modes_, &mq_desc);
  // ... 检查 aidl_retval, 初始化 FMQ ...
}
```

BluetoothAudioClientInterface::StartSession() 是蓝牙协议栈侧向 Audio HAL 发起
"打开音频通路"的核心动作。
- `provider_` 是已绑定的 IBluetoothAudioProvider AIDL 接口（由对端 Audio HAL 实现）
- `BluetoothAudioPortImpl` 是反向回调：Audio HAL → 蓝牙栈（流控制命令如 SuspendStream）
- `mq_desc` 接收 Fast Message Queue 描述符 —— 后续音频数据就通过这条 FMQ 高速传输，
  不走 Binder（避免延迟）。等价于 Java 的 SharedMemory / MemoryFile。
- `latency_modes_` 传入 FREE 或 LOW_LATENCY，影响 Audio HAL 的 buffer 策略。
