# Android 16 车载蓝牙学习资料文档质量标准

日期：2026-05-16  
适用范围：`doc/学习资料` 下所有章节，以及 `开发计划.md`、`开发跟踪记录.md`、`源码索引.md`、`问题排查记录模板.md`、`源码行号校准清单.md`

## 1. 总体目标

这套资料的目标不是“写得像教程”，而是“读完能顺着源码定位问题”。因此每一章都要满足：

- 能回到真实源码路径。
- 能解释清楚 Java -> JNI -> Native 的主链路。
- 能把问题现象映射到可观察点。
- 不虚构当前仓库没有的实现。

## 2. 强制标准

1. 每章必须出现真实源码路径和函数名。
2. 每个关键流程章节必须至少有 1 张 Mermaid 图或等价结构图。
3. 每章必须至少有 1 组练习、排查任务、命令或日志观察点。
4. 涉及 Profile 的内容必须标清边界，不混写不同 Profile 的职责。
5. 涉及厂商互联方案时，必须明确标注“仓库外/外部依赖/推断场景”。
6. 所有 C++ 解释必须绑定实际源码例子，不能空讲语法。
7. 行号只做锚点，不当作稳定契约；路径和函数名优先。
8. 文档里不保留与最终顺序冲突的描述，尤其是“开发调试准备”必须最后。

## 3. 章节模板

推荐结构：

1. 学习目标
2. 场景或问题
3. 调用链图
4. 源码片段与说明
5. 关键概念表
6. 排查/练习

如果某章是索引型内容，可以弱化流程图，但不能缺少源码锚点和导航价值。

## 4. 代码质量检查项

| 检查项 | 要求 |
| --- | --- |
| 术语一致 | 同一对象在全文只用一个主称谓 |
| 路径真实 | 路径必须来自当前仓库 |
| 函数可追 | 关键调用链至少两跳可追 |
| 图文一致 | Mermaid 图里的节点必须能在正文找到 |
| 不夸大 | 外部功能不写成仓库内实现 |
| 可复查 | 重要结论尽量有 `rg -n` 或日志观察点支撑 |

## 5. 专题补充标准

- 音乐专题必须覆盖连接、播放控制、音量、无声排查。
- 电话专题必须覆盖连接、SCO、拨号、状态回调。
- BLE/GATT 专题必须覆盖 scan、connect、discover、read/write、notify、MTU。
- 手机互联专题必须明确蓝牙侧边界，不能写成厂商协议说明书。
- 故障排查专题必须按现象组织，不按源码文件堆砌。

## 6. 交付检查

在提交一轮文档前，至少检查：

- 章节顺序是否与计划一致。
- 是否存在 `TODO`、`未开始`、`待处理` 等残留状态。
- `99-开发调试准备.md` 是否仍在最后。
- `问题排查记录模板.md`、`源码行号校准清单.md` 是否能支撑后续案例沉淀。

## 7. 教材级新标准

为了满足“让 Android Framework 与 C++ 开发小白成长为蓝牙 Framework 定制专家”的目标，后续所有补充内容还必须满足：

1. 有成长路径：资料必须告诉读者先学什么、后学什么、每阶段产出什么。
2. 有能力验收：每个阶段必须有可检查的能力目标，不能只列阅读材料。
3. 有实战任务：每个关键专题至少能落到一个排查或定制任务。
4. 有答案闭环：练习题必须有参考答案或讨论要点。
5. 有案例牵引：高频车载问题必须能映射到 `97-真实案例库.md`。
6. 有定制意识：不仅解释源码，还要说明修改点、影响范围、验证方案。
7. 有边界意识：Settings、system_server、厂商互联协议等仓库外内容必须标注边界。
8. 有复盘机制：真实问题应沉淀到案例库和跟踪记录。

## 8. 专家培养验收标准

如果读者完成全部学习资料，应能做到：

- 画出 Android 蓝牙 Framework 到 Native Stack 的完整分层图。
- 对 A2DP、HFP、GATT 各写出一条 Java -> JNI -> BTIF -> BTA/Stack 调用链。
- 使用 `rg`、logcat、dumpsys、snoop 定位至少 3 类车载蓝牙问题。
- 读懂蓝牙源码中的 `do_in_main_thread`、接口表、callback、`std::move`、智能指针。
- 设计一个小型 Framework 定制方案，包括改动点、风险、验证和回归。
- 将真实问题整理成案例卡，明确根因层级和证据链。
